Part 1 — What is Vibe Coding?

Vibe Coding = building software by talking to AI in natural language. You describe the app, features, and style; the AI writes the code, sets up files, and iterates with you. It is messy by design: you iterate, test, fix, repeat.

Mindset rules:

Start with a plan (small, concrete scope).

Build in tiny slices. Test after each slice.

When something breaks, copy the error into the AI and say “fix this.”

Save checkpoints. If needed, roll back and try again.



Part 2 — The Restaurant Analogy 🍽️

Goal: make tech concepts intuitive for non‑devs.

Frontend = Dining area

What users see and touch (pages, buttons, forms, animations).

Backend = Kitchen

Where work happens out of sight. Business logic, rules, workflows.

Database = Pantry

Where ingredients/data are stored (users, tasks, orders).

API = Waiter

Carries requests/results between the dining area and the kitchen/pantry.

Authentication = Host stand

Checks reservation/ID and hands out room keys (access tokens).

Server = Restaurant manager

Oversees operations, schedules, and the flow of work.

Hosting = The building

The place that houses everything and serves guests on the internet.

Edge functions = Service desks around the hotel/restaurant

Small stations near the guests for fast, specialized actions (e.g., “pool towel desk” → localized compute near the user).



Part 3 — Core Jargon in Plain English

HTML / CSS / JS → structure / style / interactivity.

CRUD → Create, Read, Update, Delete. The 4 basic data actions.

Domain / DNS / IP → name / phone‑book / numeric address so browsers find your app.

Server vs Hosting → server = the computer running your code; hosting = the service that gives you servers, SSL, deployments, and a public URL.

JSON → simple text format APIs use to send/receive data.

Part 5 — The 3‑Stage Prompting Workflow (PRD Journey)

Why this order: Better structure → fewer errors → faster builds.

Stage 1 — Raw ask

“Build me a project‑management app with Kanban boards.”

Stage 2 — Turn it into a PRD

Ask a reasoning model (e.g., Claude/GPT) to write a Project Requirements Document: features, data models, pages, states, edge cases.

Stage 3 — Platform‑optimized prompt

Paste the platform’s best‑practice guidelines (e.g., Bolt’s) into your chat and say, “Rewrite my PRD into a single Bolt‑optimized prompt.”

Use that in Bolt to spin up the whole project structure in one go.

Rule of thumb: Decompose thinking. Use one AI to plan, another to build. Short, iterative follow‑ups beat giant one‑shot prompts.

Part 8 — Security Basics You Repeatedly Saw

Never expose API keys in the frontend. Store in Secrets or .env on the server.

Use role‑based DB access and validate inputs on the server.

Prefer third‑party auth (Clerk, etc.) so you don’t hold raw passwords.

Back up the DB; keep production data separate from test data.



Part 9 — Debugging Flow (The “Don’t Panic” Loop)

Reproduce the issue.

Copy the exact error text into your AI builder.

Ask for a fix. If stuck, roll back to a known‑good checkpoint.

Add small changes, test again.

Common errors & quick actions

Module not found → install dependency; check import path.

Undefined variable / prop → verify state/props and component ownership.

DB connection failed → re‑link project to Supabase; verify env/secret names.

Auth not persisting → ensure redirect after login and userId saved on write.

Part 12 — One‑Liner Answers for Q&A

Q: Server vs Hosting — what’s the difference? A: A server is the computer/manager that actually runs your code and jobs. Hosting is the provider and place that keeps your app online and reachable (compute, storage, SSL, deploys). One is the worker, the other is the workplace.

Q: Why keep API keys hidden, and where? A: Keys identify and bill you. Put them in backend environment variables or platform Secrets, never in frontend files. Calls to AI models should originate server‑side or via secure functions.

Q: Can my vibe‑coded site use WordPress as the backend? A: Yes. Treat WordPress as the kitchen and expose data via the WordPress REST API or GraphQL (WPGraphQL). Your React frontend (Bolt) calls those endpoints for posts, users, etc.

Q: Can I use MongoDB or other DBs instead of the built‑in one? A: For MVP speed, use Bolt DB (Supabase). You can integrate Mongo/Postgres yourself, but it’s extra wiring. When you scale, move to a dedicated DB with migrations and observability.

Q: Should users bring their own AI API key? A: Usually no — poor UX. Keep your key in the backend and price the feature to cover usage. For power users, you can offer a “use your own key” toggle.

Q: Why not use Bolt’s AI to also power the in‑app AI feature? A: Bolt’s AI writes your code; it isn’t an API for your users. Your app should call a model provider (OpenAI/Anthropic/etc.) with your server‑side key.

Q: Claude vs GPT — which to plan with? A: Both work. Many builders like Claude for PRDs and prompt rewrites and GPT for deep reasoning. Use whichever feels clearer to you.

Q: Bolt vs Cursor — when do I switch? A: Build and validate in Bolt. When you gain traction or need reliability, push to GitHub and continue in Cursor to harden tests, security, and scale.

Q: Custom domains and DNS — how do I connect them? A: After deployment, add your domain in hosting settings. Copy the required DNS records (A/CNAME) into your domain registrar. Wait for propagation; SSL will auto‑provision.

Q: Free‑tier tricks? A: Start on the free tier to prototype. When credits run out, sync to GitHub so your work is safe. Upgrade only when you need live users or private repos.

Q: Privacy — can I keep my idea offline? A: Yes. Use self‑hosted/open‑source builders or local models through OpenRouter/OLLama. Keep code in private repos and secrets in local env vars.

Q: 21st.dev — how do I insert those fancy sections? A: Copy the component’s prompt, paste into Bolt, and include any listed install commands. Do this early so dependencies install cleanly.

Say it Super Simply Servers work. Hosting is the building. Keys are badges. WordPress can be your kitchen. Use the right tool for the stage you’re in.
